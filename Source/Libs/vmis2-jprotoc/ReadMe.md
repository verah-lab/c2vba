## About

Main goal of this project is to generate simple POJOs along with the classes generated by protobuf and to provide
methods to convert a proto generated object to a pojo and vice-versa.

This project is a code generation plugin for the [Protocol Buffers](https://developers.google.com/protocol-buffers/)
protoc compiler to use with the [Maven Protobuf Plugin](https://www.xolstice.org/protobuf-maven-plugin/). 
It is based on [jprotoc](https://github.com/salesforce/grpc-java-contrib/tree/master/jprotoc) a part of the Salesforce
[gRPC](https://grpc.io/) contribution. 

The protobuf-maven-plugin allows protoc plugins written in java by creating executables on-the-fly from java classes.
jprotoc provides a framework to build your own plugins. 

## Usage

The plugin can be used with Maven as shown below:

````xml
<properties>
    <protobuf.version>${insert_latest_version_here}</protobuf.version>
    <grpc.version>${insert_latest_version_here}</grpc.version>
    <jprotoc.version>${insert_latest_version_here}</jprotoc.version>
</properties>

[...]

<extensions>
    <extension>
        <groupId>kr.motd.maven</groupId>
        <artifactId>os-maven-plugin</artifactId>
        <version>1.6.2</version>
    </extension>
</extensions>

[...]
<!-- compile *.proto files -->
<plugin>
    <groupId>org.xolstice.maven.plugins</groupId>
    <artifactId>protobuf-maven-plugin</artifactId>
    <!-- common configuration for all executions -->
    <configuration>
        <clearOutputDirectory>false</clearOutputDirectory>
        <protocArtifact>com.google.protobuf:protoc:${protobuf.version}:exe:${os.detected.classifier}</protocArtifact>
    </configuration>
    <executions>
        <!-- execution to compile the proto files without grpc plugin; also attach '*.proto' files
            and generate DescriptorSet file ('*.protobin') (must be done only once because otherwise it will
            be attached twice to the build and the double 'deploy' of the same protobin artifact fails) -->
        <execution>
            <id>protobuf-compile</id>
            <phase>generate-sources</phase>
            <goals>
                <goal>compile</goal>
            </goals>
            <configuration>
                <attachProtoSources>true</attachProtoSources>
                <writeDescriptorSet>true</writeDescriptorSet>
                <includeSourceInfoInDescriptorSet>true</includeSourceInfoInDescriptorSet>
                <includeDependenciesInDescriptorSet>true</includeDependenciesInDescriptorSet>
                <attachDescriptorSet>true</attachDescriptorSet>
                <descriptorSetClassifier>descriptorSet</descriptorSetClassifier>
                <protocPlugins>
                    <protocPlugin>
                        <id>vmis2</id>
                        <groupId>de.heuboe.asfinag</groupId>
                        <artifactId>vmis2-jprotoc-plugin</artifactId>
                        <version>${jprotoc.version}</version>
                        <mainClass>de.heuboe.vmis2.jprotoc.Proto2PojoGenerator</mainClass>
                    </protocPlugin>
                </protocPlugins>
            </configuration>
        </execution>
        <!-- execution to compile the proto files with the grpc plugin -->
        <execution>
            <id>protobuf-compile-custom</id>
            <phase>generate-sources</phase>
            <goals>
                <goal>compile-custom</goal>
            </goals>
            <configuration>
                <attachProtoSources>false</attachProtoSources>
                <writeDescriptorSet>false</writeDescriptorSet>
                <pluginId>grpc-java</pluginId>
                <pluginArtifact>io.grpc:protoc-gen-grpc-java:${grpc.version}:exe:${os.detected.classifier}</pluginArtifact>
            </configuration>
        </execution>
    </executions>
</plugin>

<!-- place the generated FileDescriptor file (*.protobin) in the main artifact -->
<plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>build-helper-maven-plugin</artifactId>
    <executions>
        <execution>
            <id>add-protobin-resource</id>
            <phase>generate-resources</phase>
            <goals>
                <goal>add-resource</goal>
            </goals>
            <configuration>
                <resources>
                    <resource>
                        <directory>${project.build.directory}/generated-resources/protobuf/descriptor-sets</directory>
                    </resource>
                </resources>
            </configuration>
        </execution>
    </executions>
</plugin>
````

    <!-- Annotation processor used to build ProtoTransferCatalog lists for the ServiceLoader -->

<dependency>
    <!-- Annotations only -->
    <groupId>com.fasterxml.jackson.core</groupId>

<!-- optional dependencies (in case the proto files contain service definitions) -->

- [Project lombok](https://projectlombok.org/) is used for easy immutable creation.

## Preconditions

- `option java_multiple_files = true;` must be used in proto files.

## Features

- generates Pojo-Classes from protobuf definitions.
  - generates static to and from methods
  - generates 'Transfer' class: Used for generic access
- nested classes are allowed.

### Add interface version to protos

````proto
import "heuboe/protobuf/InterfaceVersion.proto";

option (.heuboe.protobuf.interface_version) = "x.y.z";
````

Contains the version of the library/project that contains the proto file.

See also:

- `InterfaceVersionUtils.getInterfaceVersion(FileDescriptor)`
- `InterfaceVersionUtils.getInterfaceVersion(GenericDescriptor)`

### Add references to other types

````proto
syntax = "proto3";

import "heuboe/protobuf/Documentation.proto";

// A simple message with a reference
message MessageWithSimpleReference {

	// A field that references the TargetMessage.id field (validated)
	string targetId = 1 [(.heuboe.protobuf.extRef) = { type: "de.heuboe...TargetMessage", field: "id" }];

}

// A message with a composite reference
message MessageWithCompositeReference {

	// A field that references something else (not validated)
	CompositeRef target = 1;

	// A message that is a reference to a TargetMessage
	message CompositeRef {

		// The target type of the reference (validated)
		option (.heuboe.protobuf.compositeTypeRef) = "de.heuboe...TargetMessage";

		// The fields that reference the remote attributes (validated)
		string name = 1 [(.heuboe.protobuf.extRef) = { field: "name" }];
		string version = 2 [(.heuboe.protobuf.extRef) = { field: "version" }];

	}

}
````

> **Note:** The jprotoc-plugin validates, that both the referenced target type and field exist. It does not validate
> whether the field types match. You can disable the (existence) validation by prefixing them with `~`.

See also: `DocumentationUtils.getExternalReference(FieldDescriptor)`

### Stereotype

````proto
syntax = "proto3";

import "heuboe/protobuf/Documentation.proto";

// A message that is a container for entities
message ContainerMessage {

	option (.heuboe.protobuf.stereotype) = CONTAINER;

	string iid = 1;
	repeated EntityMessage entities = 2;

}

// An entity message with a unique identity
message EntityMessage {

	option (.heuboe.protobuf.stereotype) = ENTITY;

	string iid = 1;
	string name = 2; // Unique
	repeated DataTypeMessage childrenWeights = 3;

}

// A message that represents a datatype message without a unique identity
message DataTypeMessage {

	option (.heuboe.protobuf.stereotype) = DATATYPE;

	string iid = 1;
	string childName = 2;
	uint32 weight = 3; 

}
````

**Hints for categorizing messages:**

- `CONTAINER`: Only an iid and a repeated field with a type that is an `ENTITY`
- `ENTITY`: A message with a unique identifier (might use multiple fields including those in sub messages)
- `DATATYPE`: A message without a unique identifier that needs additional context to be useful

See also: `DocumentationUtils.getStereotype(Descriptor)`

> **Note:** The jprotoc-plugin validates, that all messages specify a stereotype.
> You can turn this off by specifying the `--ignoreAbsentStereotype` command option.

### Required

````proto
message CardinalityMessage {

	string childName = 1 [(.heuboe.protobuf.required) = true];
	string weight = 2 [(.heuboe.protobuf.required) = false];
	string hint = 3; // implicitly required = true

}
````

Annotation that marks a field as optional/potentially absent.  
By default fields should be considered required.

> **Note:** `repeated` fields are always considered to be `0..*`.

> **Note:** The annotation is used for documentation purposes only,
> it does not prevent getting/setting/sending/receiving invalid values.

See also: `DocumentationUtils.isRequired(FieldDescriptor)`

## vmis2-jprotoc-transferinterface

The `vmis2-jprotoc-transferinterface` module, which you need in your classpath when using generated POJOs will offer you some utility classes for easily converting POJOs to PROTOs (and vice versa) and other useful convenient methods to work with the generated classes.

Mainly these are the classes 
* `de.heuboe.vmis2.jprotoc.utils.ProtoPojoUtils`
* `de.heuboe.vmis2.jprotoc.utils.ProtoTransferRegistry`

When you use these classes the `ProtoTransferRegistry` will be initialized with meta information about all generated PROTO/POJO classes which will be cached in memory.
The `ProtoPojoUtils` class, wich provides the public API for most PROTO/POJO operations, makes use of the _ProtoTransferRegistry_ and the cached information there.

However, if an application has a lot of PROTO/POJO classes in the classpath, this caching may become very large and consume a lot of memory.
To disable the caching the system property

* `proto.transfer.registry.initialization.disabled=true`

can be used.  

This disables the scan of the classpath for ProtoTransferCatalogs and the caching of all BaseTransfer instances in the ProtoTransferRegistry which saves a lot of memory, especially if you have many Proto classes in the classpath.
However, it makes the use of the ProtoTransferRegistry class obsolete, since it no longer caches any information.  
If you need a transfer class to a specific proto, you have to find an alternative way in that case.
The `ProtoPojoUtils` class, which is usually used when such operations are needed, has various fallback mechanisms for this and can still be used - even if the ProtoTransferRegistry class has not been initialized with the BaseTransfer classes.

As a rule of thumb, if you have only a few proto classes in the classpath, or are likely to use most proto classes in the classpath, then stick with the default.

But if you have many proto classes in the classpath and use only a few of them, then disable the ProtoTransferRegistry initialization and observe whether this significantly changes the memory consumption of your application.
In this case it might be useful to disable the initialization of the ProtoTransferRegistry.
